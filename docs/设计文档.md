# 设计文档

## 1. 目标

做一款浏览器内可完成的双人协作解谜平台跳跃：《霜焰双行》。玩家在同一关卡同时控制焰行者「烬」与霜行者「朔」，利用元素对立、材料连锁和场景细节通关。

成功标准：

- 纯前端，无必须后端
- 18 关，第 1 关即为中等偏难协作教学，全程难于常见网页双人过关
- 角色与场景为风格化写实，禁止像素堆叠作为主视觉
- 单人双键位与双人同机都能通关
- 可 Dokploy 静态容器部署

## 2. 范围

### 已规划、阶段 B 起实现

- 双角色不对称能力与元素伤害
- 固定时间步物理、数据驱动关卡
- 封面 / 说明 / 选关 / HUD / 设置 / 结算
- localStorage 存档与 JSON 导出导入
- 18 关（见 [关卡设计.md](./关卡设计.md)）

### 明确不做

- 联机、账号、排行榜服务器
- 像素风或纯色块人
- 移动端作为一等输入（可提示键鼠）
- 一键托管自动通关
- 第 1–5 关检查点

## 3. 架构

```
┌─────────────────────────────────────────────┐
│ React UI 壳（路由、菜单、设置、暂停遮罩、结算）│
│  不持有物理真相，只发 InputIntent / 读 ViewModel │
└────────────────────┬────────────────────────┘
                     │
┌────────────────────▼────────────────────────┐
│ GameRuntime（Pixi Application + 固定步进）   │
│  Input → Sim(1/120s) → View(1/60s) → Audio   │
└──────┬───────────┬───────────┬──────────────┘
       │           │           │
   Actors      World/Hazards   PuzzleSystems
       │           │           │
       └───────────┴───────────┘
                   │
            LevelDocument JSON
```

原则：模拟层与渲染层分离。测试只跑 Sim。Pixi 精灵不是碰撞体。

## 4. 模块边界

| 模块 | 职责 | 不得依赖 |
|---|---|---|
| `engine/loop` | 固定 dt、螺旋补偿、暂停 | UI 组件 |
| `engine/input` | 键位绑定、缓冲、同帧双角色意图 | Pixi |
| `engine/physics` | AABB、单向台、移动台、斜坡、摩擦 | 关卡叙事 |
| `engine/camera` | 双人约束框、死区、失联警告 | 解谜图 |
| `actors` | 角色状态机、动画事件、元素抗性 | React |
| `world` | 材质、液体体积、伤害场、可燃/可冻 | UI |
| `systems/puzzle` | 压板、门、光束、齿轮图 | 精灵路径 |
| `systems/rescue` | 8s 救援窗、祭坛电荷 | 菜单 |
| `systems/score` | 时间、死亡、救援、三星 | 渲染 |
| `levels` | 加载校验 JSON | Pixi 滤镜 |
| `ui` | 页面与无障碍 | 物理内部结构 |

## 5. 技术选型

| 决策 | 选择 | 理由 | 备选与否决 |
|---|---|---|---|
| UI | React 19 + TS + Vite | 与工作区前端项目一致；菜单/设置适合组件树 | Vue 3 可行，混用禁止 |
| 渲染 | PixiJS 8 | 高分辨率精灵、滤镜、分层光照，比 DOM 游戏强 | Phaser 渲染可用但 Arcade 物理否决 |
| 物理 | 自研固定 1/120s | 平台跳跃需要土狼时间、跳跃缓冲、单向台；Matter 对平台跳跃不稳定 | 用 Matter 只做装饰破碎，不做角色真相 |
| 动画 | 帧序列 + 状态机；布料/发丝用次级骨骼或着色器摆动 | 写实角色需要多状态；阶段 B 先保证 11 个状态循环 | Spine 运行时作为阶段 E 可选升级 |
| 关卡 | JSON + 碰撞网格 48px | 增关以数据为主 | 禁止每关复制一份 Game.tsx |
| 存档 | localStorage + 导出文件 | 无后端 | — |
| 部署 | Docker 多阶段 + Caddy:3000 + /healthz | 对齐 audio-convert / homepage 的 Dokploy 习惯 | Nixpacks 裸静态作为回退 |

### 5.1 时间步

- 物理：`dt = 1/120`，单帧最多追赶 8 步，剩余进 accumulator
- 渲染：跟随显示器，状态在两物理帧间插值
- 机关计时用物理时间，不受掉帧变慢而变简单

### 5.2 单位

- 1 格 = 48 世界像素（碰撞栅格，不是像素画格子）
- 角色碰撞盒约 28×70；精灵绘制约 120×160，脚底对齐盒底
- 重力 2400 px/s²；起跳速度 900 px/s（约 3.5 格理论抛物高度）
- 水平速度：烬 380、朔 350；朔在冰面加速度低、摩擦系数 0.08（冰面系统仍属第 2 关规划）
- 土狼时间 80ms，跳跃缓冲 100ms；跳跃只响应按下沿，松键会把上升速度缩短到 52%，长按落地不会自动连跳

### 5.3 相机

- 以两碰撞盒并集外扩 4 格为约束框
- 死区 2 格，平滑跟 8Hz 左右
- 最大分离 28 格：超出则 HUD「失联」，远端角色 0.35 倍速并显示方向提示；**不传送、不自动聚拢到终点**
- 禁止把一人甩出解谜所需视野超过 1.2s 而无提示

## 6. 数据流

```
键盘 → InputMap → { ember: Intent, frost: Intent }
Intent → ActorController → 速度与动作请求
World.step：移动解析、液体、伤害、机关图、救援窗
SimSnapshot → Presenter → Pixi + React HUD ViewModel
Score/Save ← 通关或离开关卡
```

关卡加载：`fetch /levels/xx.json` → schema 校验 → 构建静态碰撞与机关节点 → 生成 Actor。

## 7. 依赖

运行时：`react`、`react-dom`、`pixi.js`、`zod`（校验关卡/存档）。

构建：`vite`、`@vitejs/plugin-react-swc`、`typescript`、`vitest`。

部署：`node:22-alpine` 构建，`caddy:2-alpine` 托管。

禁止运行时依赖后端 SDK、账号 SDK。

## 8. 约束

- 1080p 桌面目标 60fps；粒子可降，判定不可降
- 资源全部进静态包；单关纹理预算阶段 B 先不超过约 25MB 解压前
- 颜色与形状必须双通道传达危险（色盲：熔岩有上涌波纹，水有波光与涟漪）
- 无障碍：键位重绑、暂停、快速重开、减弱闪烁

## 9. 失败模型

| 失败 | 行为 |
|---|---|
| 单人致死 | 该角色倒地；8s 救援窗；另一人到本关已放置的复苏祭坛可救；超时则整关失败 |
| 双人致死 / 救援超时 | 关卡重置到关起点（1–8 关无检查点；9+ 长关可有 1 个） |
| 软锁检测 | 可重开；阶段 C 起对「箱子落入不可及伤害区」提供 4s 后提示重开，不自动重置以免破坏思考 |
| 存档损坏 | 校验失败则忽略并备份 `frostfire.sanctum.bak`，从默认进度启动 |
| 关卡 JSON 非法 | 开发模式抛错；生产选关显示「关卡数据损坏」 |
| 构建/镜像 | 缺 lockfile、缺 dist、healthz 非 200 则失败退出 |

救援代价：祭坛消耗 1 点本关「誓火/霜约」电荷。电荷也用于可选支路或三星条件。用救援通常失去第三星。第 1–11 关电荷主要用于评分；第 12 关把电荷编入主解法分叉。

## 10. 演进边界

- 可加：Spine、手柄、更长视差、语言包
- 不可在无 schema 版本迁移时改存档字段
- 不可把物理 dt 改成可变步长
- 新机制必须先改 [关卡设计.md](./关卡设计.md) 规则引入表，再写系统，再进关卡

## 11. Key Decisions

1. **React 壳 + Pixi 画布，不把游戏画在 DOM。** 写实光影与 60fps 角色无法用 div 堆。
2. **自研平台物理，不用 Matter 做角色。** 协作关对可预测跳跃的需求高于刚体堆箱子。
3. **18 关数据驱动。** 避免 18 份页面逻辑分叉。
4. **第 1 关就上完整对立伤害 + 引开 + 周期窗 + 双压板限时闩。** 满足「初始难度不能太低」，用预示保证公平。
5. **风格化写实帧动画，不用像素瓦片当角色。** 碰撞可用不可见网格，可见层必须是绘制场景。
6. **Dokploy 走 Caddy 3000 + healthz + 非 root。** 与工作区已有前端镜像习惯一致。
